# Architecture

## Phase 1B read-only flow

```text
BookingTarget / CLI
    -> authenticated local controller
    -> WebSocket broker on 127.0.0.1
    -> paired MV3 extension service worker
    -> isolated content script
    -> fixed MAIN-world RestaurantsAvailability operation
    -> in-Chrome allowlist projection
    -> strict bridge schema
    -> invariant-checking slot normalizer
    -> ReservationSlot[]
```

The user owns and controls the normal Chrome session and performs ordinary
OpenTable sign-in. Node never launches Chrome, reads a Chrome profile, receives
cookies, or receives account credentials. The extension is a narrow transport,
not an automation engine.

The loopback broker binds to `127.0.0.1` only. A one-use, five-minute pairing
code transfers a random 256-bit credential to the extension. Subsequent
extension and controller connections authenticate before other messages are
accepted. Protocol messages have an explicit version, Zod schema, ID, and
deadline. Unknown fields and unknown message types are rejected.

The MAIN-world bridge learns `RestaurantsAvailability` only when the normal
page uses it. The bridge prefers the exact same-origin fetch generated by the
normal page because it already contains the page's transformed operation. When
no fetch template is available but a live Apollo client/document is exposed,
it can reuse that document. The narrow fetch path keeps its request template in
page memory. It can replay only that exact observed
read operation with validated variables. Request URL, headers, persisted-query
details, and browser credentials stay inside the page. There is no caller-
supplied operation name, document, JavaScript, URL, header, or arbitrary fetch
capability.

The isolated content script projects the result onto an allowlist before it can
reach Node. Allowed response fields are restaurant ID, day offset, availability,
relative/authoritative time, seating attributes, and seating type. Availability
tokens, booking hashes, cookies, authorization data, account data, and all
unrecognized fields are removed. The Node normalizer then checks request/
response restaurant, date, time, and party invariants and fails closed on
malformed or contradictory data.

Readiness metadata contains only the canonical OpenTable origin and pathname.
All URL query parameters and fragments are stripped inside Chrome so opaque
page state cannot cross the bridge as part of a status message.

## Permission rationale

- `storage`: retain the random local bridge credential and configured port.
- `https://www.opentable.com/*`: run the two bridge scripts only on OpenTable's
  canonical web origin.
- `http://127.0.0.1/*`: permit the extension's WebSocket connection to the
  loopback bridge. The server independently refuses non-loopback binding.

The extension requests no cookies, tabs, scripting, webRequest, debugger,
native messaging, downloads, history, identity, or broad website permission.

## Adapter separation and future flow

`OpenTableReadAdapter` exposes only authentication checking and slot discovery.
The Phase 1B class implements that interface and has no prepare, lock, book,
cancel, favorites, or profile method. `OpenTableBookingAdapter` remains a
separate future interface required by the booking engine; Phase 1B does not
instantiate or simulate it.

The existing provider-neutral policy model remains future-facing: a prepared
booking would carry an opaque in-memory handle and a normalized preview, with
unknown financial terms failing closed. No such provider write path exists in
this phase.

## Failure and trust boundaries

Authentication required/expired, challenge content, access denial, rate
limiting, unavailable page operations, malformed payloads, request invariant
mismatch, and ambiguous local times do not produce slots. Transport failures
may be retried conservatively; safety-sensitive failures pause.

The browser page is untrusted. The extension is allowed to read only the fixed
availability result and must sanitize it before crossing into the local broker.
The loopback network is also untrusted until credential authentication succeeds.
Local malware with the user's account privileges is outside this boundary and
could already access local files or control Chrome.

The design explicitly excludes CAPTCHA solving, anti-bot/access-control
evasion, stealth automation, proxy rotation, fingerprint impersonation,
rate-limit bypass, and hosted credential/session handling.

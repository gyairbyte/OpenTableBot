# OpenTable Browser Session

Phase 1 uses ordinary installed Google Chrome through Playwright. It is headed,
interactive, read-only, and isolated in a dedicated persistent profile.

## Profile and authentication

The default profile is:

```text
.local/opentable-browser-profile/
```

That directory is ignored by Git and may contain cookies and other sensitive
browser-managed session state. Never copy it into source control, logs,
fixtures, or support messages. The adapter never exports cookies or asks for an
OpenTable username or password.

To use another dedicated location in PowerShell:

```powershell
$env:OPENTABLE_BROWSER_PROFILE_DIR = "C:\path\to\dedicated-opentable-profile"
```

Do not point this variable at an everyday Chrome profile.

Start normal interactive login:

```sh
npm run opentable:login
```

A dedicated Chrome window opens on OpenTable. Use the site's normal sign-in
experience, then return to the terminal and press Enter. The command navigates
to the normal dining dashboard and reports a structured authenticated or
unauthenticated result. CAPTCHA, challenge, block, or access-denied pages are
reported and processing stops; the application does not solve or bypass them.

Check the same persisted session later:

```sh
npm run opentable:check-auth
```

Only one process should use the dedicated profile at a time.

## Read-only availability smoke test

After authentication succeeds:

```sh
npm run opentable:slots -- \
  --restaurant-id 12345 \
  --restaurant-name "Example Restaurant" \
  --date 2026-09-01 \
  --party 2 \
  --earliest 18:00 \
  --latest 20:00 \
  --preferred 19:00 \
  --timezone America/New_York
```

Use the provider restaurant ID represented in the normal availability response
and the restaurant's real IANA time zone. The command navigates a normal search
page, observes the response generated by that page, verifies restaurant/date/
party invariants, and prints normalized slots. It does not click a time, enter
checkout, prepare or lock a slot, submit a reservation, or modify the account.

Network-response observation is primary in Phase 1. No DOM fallback is used;
if structured availability cannot be observed or verified, the adapter fails
closed with an unexpected or malformed response instead of guessing.
